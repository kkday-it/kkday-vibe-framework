# 非工程可讀性規則 + 個資/憑證安全邊界

填每一份 handoff 檔前讀這份。這些是兩案（排班、打風）踩過、以及獨立審查（agy）抓出的坑，固化成規則。

## A. 非工程可讀性（讀者是 PM 本人，執行者是他的 AI）

核心矛盾：同一份 G0-EXPORT-GUIDE 主要給 AI 讀執行，但 PM 本人也會看。原則是**技術內容全留給 AI，另配白話給 PM，並清楚標「誰做」**——不要為了 PM 好讀就刪掉 AI 需要的技術料。

1. **工具名統一。** 別在同一包裡混用「Claude Desktop」「Claude Code」「你的 AI」。PM 分不出視窗軟體和命令列工具，會卡在「我到底開哪個」。全包統一一個稱呼（建議「你電腦上的 Claude」）。

2. **每個步驟標【誰做】。** 匯出清單每項前面標 `【AI 自動跑】` 或 `【需 PM 點畫面】`。PM 一眼知道哪幾步要親自到 Dashboard 點/截圖，其餘不用管。清單頂部放一句總引導：「預設你的 AI 自動跑；標【需 PM 點畫面】的才要你動手，SQL 你不用懂。」

3. **技術警告配白話。** 像「選 Session pooler / Port 5432 不要 Transaction pooler」這種對 AI 是必要的（抄錯 pg_dump 直接失敗），但 PM 看到會緊張。作法：保留技術行給 AI，上面加一句「🟢 白話：模式選『Session』那個；不確定就把整串貼給你的 AI 檢查」。

4. **除錯/驗證段標清楚是給 AI/RD 的。** 「在空本機 Postgres 重跑 schema 驗證」這類 PM 電腦根本做不到、看不懂。標題就寫「（這段給你的 AI / RD 做，PM 不用跑、不用看懂）」，並加一句「看到紅字錯誤不用緊張，常是缺 PaaS 專屬相依，不代表匯出錯，整包交 RD 判斷」。

5. **未來階段的背景別塞進 PM 主文。** 平台談判、24/7 縮容、egress 這些是重構階段技術細節，對「現在要做 G0」的 PM 是認知負荷。壓成一句「這些技術決定已拍板、RD 負責，你只要專心把 G0 做完」，細節放 `docs/`。

6. **CLI/加速選項標「選配」。** 「Supabase CLI 登入能更快下載」對 AI 有用，但要標「這是給你的 AI 的加速選項，PM 本人不用理解、沒有也沒關係」，免得 PM 以為環境沒裝好不敢往下。

## B. 個資 / 憑證安全邊界

遷移匯出天生會碰到個資（客戶/員工資料）與憑證（連線字串、token、webhook URL、API key）。交接包每一處都要守住邊界，否則 handoff 自己就是外洩源。

1. **含個資的匯出物不進版控、走安全通道。** 資料 dump（如 `*_data.sql`）只交 RD 另存於安全位置，不進 git、不進 repo。schema/function/policy 這類技術定義才可入 repo。

2. **憑證只在 PM 機器上給他的 AI 用。** 連線字串/token 不傳給第三方。某工具 PM 電腦缺、需 RD 代跑時，**走安全管道**（當面/私訊），別貼公開頻道（Slack channel 等）。START-HERE 的「不外傳」和 G0-guide 的「缺工具找 RD」要對齊，別自相矛盾。

3. **可轉傳報告 = 去個資的安全子集。** 若要產「完成報告」給主導者看（讓進度公開可見），它**只能含狀態 + 結構摘要 + 數字（row counts、表名、function 名）**，**禁**：資料列內容、任何個資、連線字串、token、webhook URL、API key。報告開頭放一句聲明「本報告僅含狀態與結構摘要，不含個資、憑證、原始資料列」——這句就是它能被轉傳的依據。

4. **別讓自動化把原始匯出送出去。** 不要設計「AI 自動把 G0 整包上傳分享連結 / Slack」的流程——那會把個資送進留存、可搜尋的地方。要自動通知就只送去個資的摘要報告，且私訊（DM）不進頻道。

## C. 誠實 / 留痕（讓報告「公開公正」）

1. **失敗和空的照實標，別全綠交差。** 完成度用 ✅/⚠️/❌/➖/⏳；「查不到」要出現，不能藏。
2. **查不到 ≠ 沒有。** 查詢空結果標「待確認」，別當結論；失敗查詢留原始錯誤（不含憑證）。
3. **預期 vs 實際對照。** 報告用「預期（來自工程師評估文件）vs 實際（G0 撈到）」兩欄，讓人一眼看出現實跟評估合不合（多/少一支 function、少一張表、RLS 沒開）。
4. **留痕。** 跑指令 `2>&1 | tee`；保留 raw 輸出與 `.err`；每階段收尾記一筆（日期/做了什麼/下一步交給誰）。
